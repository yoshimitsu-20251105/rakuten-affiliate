## ID

brief-2026-10-13-product-data-freshness-disclosure

## Objective

商品ページの「情報取得日」「最終更新日」が、実際の商品データの取得日・ページ内容の変更日ではなく、日次生成の実行日(今日)になっている。また、同じページのProduct構造化データ(JSON-LD)が、古いスナップショットの価格・レビューを、在庫「あり」として検索エンジンに伝えている。ユーザーとGoogleの両方に対して、表示する情報の鮮度を実態に一致させ、確認できていないことを確認済みのように伝えない。あわせて、価格・在庫・レビューが古いまま残る問題への対応を、最小コスト案として決める。

## Business KPI

信頼性(表示と構造化データの正確さ)を第一とし、Traffic(Googleの品質評価に対するリスク低減)、Measurement(データの鮮度を判断できる状態)。Revenueへの直接効果は現時点で測れない(後述のEvidence参照)。

## Hypothesis

- HYPOTHESIS: 取得日を実態どおりに表示する(確認できない場合は日付を断定しない)ことで、ユーザーの誤認リスクと、鮮度を偽っていると評価されるリスクが下がる
- HYPOTHESIS: 自動生成商品ページから、確認していない価格・在庫・外部サイト由来の評価を含むProduct JSON-LDを一時停止することで、構造化データの手動対策(リッチリザルトの対象外)を受けるリスクが下がる
- HYPOTHESIS: 表示日付を実態に合わせると、日次で約400ファイルが書き換わる状態も解消でき、PR #28の`lastmod`修正の効果が出やすくなる

### git初回追加日を「商品データ取得日」として使えるか

405記事の初回追加コミットを調べた結果(分析スクリプトは一時ファイルで、リポジトリには含めていない)。

- FACT(証明できる範囲): 320記事は、初回追加コミットの作者が`rakuten-affiliate-bot`でメッセージが`auto:`で始まり、**そのコミットの`selected-products.json`に当該`itemCode`が含まれる**(320件中320件、例外0)
  - 日次ワークフロー(`.github/workflows/`)は、商品選定(`select-products.js`)→サイト生成(`generate-site.js`)→commit・pushを同一ジョブで順に実行する
  - `select-products.js`は実行のたびに楽天APIをライブで検索し(`searchItems()`)、キャッシュを使わず、`selected-products.json`を毎回上書きする。API失敗時は空配列を返すだけで、古いデータを流用しない
  - GitHub Actionsの実行履歴(取得できた66回): 全て成功、所要時間は0.5〜3.5分、**日本時間の日付をまたいだ実行は0回**
  - したがって、この320記事は「取得した日(日本時間)=初回追加コミットの日付(日本時間)」とみなせる
  - 注意: コミット日時のUTC日付と日本時間の日付が異なるものが131件ある(UTC 15:00以降のコミット)。**日本時間の日付で判定する必要がある**
- FACT(証明できない範囲): 残り85記事は、人間のアカウントによる手動コミット(2026-08-17〜08-21)で初回追加された。ローカル実行後に後からコミットした可能性を排除できないため、**gitの初回追加日が商品データの取得日と同日であることは証明できない**
- 結論: 320記事は`snapshotDate`として使える。85記事は`estimatedSnapshotDate`として別扱いにし、ユーザー画面で「商品情報の取得日」として断定表示しない。UNKNOWNを正確な日付に変換しない

### 構造化データ(Product JSON-LD)の監査

- FACT: 記事ページのProduct JSON-LD(`generate-site.js:303-320`)は、`offers.availability`が全商品で固定の`https://schema.org/InStock`。405ページ全てで`InStock`が出力されている。`OutOfStock`等が出力されるページは0件
- FACT: 取得時点で`availability=0`の2商品も`InStock`と出力されている。`articles-data.json`の値と構造化データが矛盾している(楽天APIの`availability`は0が販売不可と理解している。ESTIMATE)
- FACT: 可視ページには在庫状況の表示がない(「在庫は変動する場合があります」「在庫を見る」の文言のみ)。つまり`InStock`は、ページ上でユーザーに見えていない情報を構造化データだけで主張している
- FACT: `offers.price`、`aggregateRating.ratingValue`、`aggregateRating.reviewCount`は、いずれも`articles-data.json`の初回取得時点のスナップショット値(最大約57日前)。価格とレビューはページ上でも同じ値が見えているため、表示との不一致はないが、「現在の価格・評価」として伝わる
- FACT: `aggregateRating`の評価は、楽天市場の購入者のレビュー集計であり、本サイト自身のユーザーのレビューではない
- FACT(Google公式ドキュメント、2026-10-13に確認): 構造化データのガイドラインは「情報を最新に保つこと」「ユーザーに見えるコンテンツだけをマークアップすること」を求めている。レビューのガイドラインは「他のウェブサイトのレビューや評価を集計しない」としている。商品スニペットは`review`・`aggregateRating`・`offers`のいずれか1つがあれば対象になる。構造化データの手動対策は、そのページのリッチリザルトの対象外とするもので、通常のウェブ検索の順位は変えない、と記載されている
- HYPOTHESIS: 外部サイト(楽天)のレビュー集計を`aggregateRating`として出力することは、上記のガイドラインに反する可能性がある
- UNKNOWN: Googleが現在この構造化データをどう扱っているか、手動対策の有無(Search ConsoleのManual Actionsレポートはこの調査では確認していない)
- UNKNOWN: 現在、リッチリザルトとして表示されているページがあるか(記事ページのほとんどが検索結果に出ていない可能性が高い)

- 記事ページへのアクセスがほぼないため、表示の誤りでユーザーが実害を受けた証拠はない(影響は主に信頼性とGoogleの品質評価のリスク)
- Googleが「情報取得日」の表示や、この構造化データを評価にどう使っているかは不明(UNKNOWN)。「ペナルティを受けている」という根拠はない。構造化データの問題は通常、リッチリザルトの対象外になるだけで、順位には影響しないと公式に記載されている
- Product JSON-LDを停止すると、商品スニペット(価格・星評価などのリッチリザルト)の対象でもなくなる。ただし、現時点で表示されている証拠はなく、現状のマークアップは誤り(`InStock`固定)と外部サイト由来の評価集計を含むため、残す実益がない
- 85記事の取得日は、実際には公開当時と同じ日付かもしれないが、それを確認する手段がない

## 表示する日付の方針(候補A・B・C)

| 案 | 内容 | 評価 |
|---|---|---|
| A | 実際の商品データ取得日を表示する | 最も正確。ただし証明できる320記事(と今後追加する記事)だけ。85記事は取得日が不明 |
| B | 実取得日が分からない場合は「本日取得」の表現を削除し、日付を断定しない | 85記事に適用する。日付がないと鮮度が伝わらないため、「取得日の記録がない」旨を明記する |
| C | 最終更新日は実際にページ内容が変わった場合だけ更新する | ページ内の「最終更新日」表示を日付で埋めると、PR #28のハッシュ計算と循環するため、表示自体を削除する方が単純 |

**推奨: A + B + C**
- `snapshotDate`がある記事: 「商品情報の取得日: YYYY年M月D日(価格・在庫・レビュー件数はその時点の情報です)」
- `snapshotDate`がない記事(85件、`estimatedSnapshotDate`のみ): 取得日を表示せず、「商品情報の取得日の記録がありません。2026年8月に公開した時点、またはそれ以前の情報で、現在の価格・在庫・レビューと異なる場合があります。」(公開日はgit履歴で確認できる事実。データが公開日より新しいことはあり得ないため、「公開時点またはそれ以前」は正しい)
- 共通フッターの「最終更新日: 今日」は削除する。ページ内容が変わった日は`sitemap.xml`の`lastmod`が表す
- ランキングページの「取得時点のもの」の文言には日付を書かず、各商品ページに取得日が書かれていることを示す(複数商品の取得日が混在するため)

## Implementation Requirements

- 表示する日付は`snapshotDate`だけを使い、生成日(`TODAY_JP`)や`estimatedSnapshotDate`を商品データの取得日として表示しない
- `snapshotDate`の既存320件への付与は、(1)初回追加コミットの作者が`rakuten-affiliate-bot`、(2)メッセージが`auto:`で始まる、(3)そのコミットの`selected-products.json`に当該`itemCode`が含まれる、の3条件を全て満たす記事だけとする。1つでも満たさない記事は`estimatedSnapshotDate`にする(推測で`snapshotDate`にしない)
- 日付は日本時間で算出する(UTC日付を使わない)
- `snapshotDate`が欠けている商品は、日付を表示せず、ビルドを失敗させない
- 実行前に、変更されるページ数と差分の代表例(`snapshotDate`あり・なし各1件)をユーザーに示す

## Measurement Plan

- 実行後、記事ページに「生成日と異なる取得日」が表示され、`snapshotDate`が入った記事の表示がその日付と一致すること。`snapshotDate`がない記事に取得日が表示されないこと
- 全ての記事ページに`application/ld+json`のProductが存在しないこと(`schema.org/Product`・`InStock`・`offers`・`aggregateRating`を含む出力が0件)。ランキングページ等のFAQPageは影響を受けないこと
- 日次コミットで変更されるファイル数が、約400件から、実際に内容が変わったページ数に減ること(PR #28のsitemap `lastmod`の日次変更数と併せて確認)
- GA4・Search Consoleは、この変更の効果指標としては使わない(アクセスが少なく判断できないため)
- **Search Consoleの「Product拡張レポートにエラーが出ないこと」は成功条件にしない**(Product JSON-LDを意図的に停止するため、Productの項目自体が出なくなる)。代わりに次を確認する: (1)対象ページに誤ったProduct JSON-LDが存在しない、(2)Rich Results Testに誤ったProduct情報を送信していない(停止前のマークアップを検証目的で送らない)、(3)通常のHTMLページとしてクロール可能(HTTP 200、`noindex`なし、self canonical、`robots.txt`で許可)

## Success Criteria

- 「情報取得日」「最終更新日」が、証明できる商品データの取得日、またはページ内容の実際の変更日を示す(または削除されている)
- 取得日を証明できない85記事で、取得日が断定表示されていない
- 自動生成商品ページに、誤った/確認していないProduct JSON-LD(固定の`InStock`、最大約57日前の価格、楽天由来の`aggregateRating`)が存在しない
- 記事ページが通常のHTMLとしてクロール可能(HTTP 200、`noindex`なし、self canonical)
- 日次の変更ファイル数が減り、日付文字列だけの変更がなくなる
- 対象LPのファイル差分が0件
- `npm test`と`npm run strategy:validate`が通る

## Kill Criteria

- 差分の代表例が意図と異なる、またはビルドが失敗する場合 → 実行を中止してrevert
- 日付以外の商品データ(価格・在庫・レビュー・名称)の可視表示が変更された場合 → 即時revert
- 記事ページが通常のHTMLとしてクロールできなくなった場合(HTTP 200以外、`noindex`の混入、canonical変更) → 即時revert

## Rollback Plan

該当コミットをrevertする。`snapshotDate`/`estimatedSnapshotDate`フィールドを追加し、日付表示を変えてProduct JSON-LDの出力を止めただけなので、revertで元の表示・構造化データに戻る(ただし元のProduct JSON-LDは誤り/未確認の値を含むため、revertは緊急時の手段とし、再開する場合はS6の条件を満たすこと)。

## Required Tests

- `snapshotDate`が表示されること、欠けていても例外にならないこと
- `estimatedSnapshotDate`だけの記事に取得日が表示されないこと
- 生成日が商品データの取得日として表示されないこと
- 記事ページにProduct JSON-LD(`application/ld+json`の`Product`)が出力されないこと。ランキングページのFAQPageは出力され続けること
- 記事ページの可視HTML(商品名・価格・レビュー表示・CTA・affiliate URL)が変更前後で同じであること(日付表示の行を除く)
- 楽天APIを呼び出すモジュールをimportしていないこと(既存の`generate-site-search-trial.test.js`の確認項目に準拠)
- 既存の`generate-site-search-trial.test.js`と`sitemap-lastmod.test.js`が通ること
- `npm run strategy:validate`、`npm test`
